## 3. The mechanism: the two regimes are not equivalent

* **UM982 (attitude-trusted):** psi is pulled onto `dualAz + 88.3 deg`. The reference is the
  antenna baseline, so its offset constant, the antenna geometry and the attitude's own
  frame-to-frame jumps sit directly in the heading. The jumps are large: 18 ... 40 deg within
  0.4 ... 3 s (13-59), and the 2 Hz HB1 lines show the same (`az=211.5 -> 160.0` in 2 s).
* **F9P (no attitude):** psi is anchored to the **IMU heading**, whose offset the bridge
  learns **against the path** (`imuhdgoff`). The path is the reference, so the attitude jumps
  cannot enter psi - and the machine does not run diagonally.

**The F9P gets by necessity the one thing the UM982 lacks: a continuous path-anchored
reference.** That is exactly Step A + Step C of `heading_recovery_concept_2026-10-04.md`.
Supporting fact: the F9P drives *better* with *worse* positions (`POS_RTK` 0 ... 32 %,
`travel_wit` valid in only 14 %/1 %/0 %/0 % of the frames), so its smoothness is not a GNSS
quality effect.

* `uni_pitch` and `roll_deg` are **identical** (r = 1.00, same sd, same median): the receiver's

### 4b. How to settle it: a 5-minute identification test (before any roll code)

Precondition (one small firmware step): log the raw BNO triple **continuously**, ~1-2 Hz, e.g.
`IMU,yaw,pitch,roll,flags`. Today only the boot line carries all three
(`DEBUG/IMU: Initial data: ...`), and `status.imuRollDeg` is the single axis the bridge chose.

Then, standing still, at the same spot:

1. three headings ~120 deg apart, ~10 s each (the operator's own test - "an der gleichen Stelle
   aus anderer Richtung");
2. one wheel on a **known** block (known roll), in two headings 180 deg apart;
3. one short drive with the receiver roll available (`roll_deg` is trustworthy, section 4).

From those numbers the scale (0.01 vs 0.1 deg), the mounting rotation (a module yaw offset
mixes roll and pitch - which is exactly what makes the reading heading-dependent) and the need
for an axis swap can be solved arithmetically. Until then the honest status is: **the IMU roll
is not a usable measurement, and no code fix should be built on a hypothesis.**

Immediate, safe step (no identification needed): an **envelope for every roll source**
(|roll| > ~15 deg -> hold/none, never published) and the IMU roll no longer preferred as the
source. That removes the impossible values without touching the machines that work.

## 6. How AgOpenGPS processes the roll (source-verified 2026-10-05)

From `SourceCode_AgOpenGPS` in this repo:

```csharp
// UDPComm.Designer.cs - AOG itself has TWO conventions:
ahrs.imuRoll = temp - ahrs.rollZero;              // PANDA/PAOGI path: value is DEGREES
rollK = imuRol * (isRollInvert ? -0.1 : 0.1);     // PGN 211 path (OUR IMUProcessor!): 0.1 deg units
rollK -= ahrs.rollZero;
ahrs.imuRoll = ahrs.imuRoll * ahrs.rollFilter + rollK * (1 - ahrs.rollFilter);  // low pass
if (ahrs.imuRoll > 25 || ahrs.imuRoll < -25) ahrs.imuRoll = 0;                  // HARD CLAMP -> 0
// guidance, all four modes - a STEERING correction:
steerAngleGu += ahrs.imuRoll * -sideHillCompFactor;      // CGuidance.cs:98
steerAngleAB += ahrs.imuRoll * -gyd.sideHillCompFactor;  // CABLine.cs:290
// CABCurve.cs:1004, CContour.cs:540; display only: GL.Rotate(imuRoll,0,0,1)
```

Consequences of a 10x roll - and it is not only the steering term (operator correction
2026-10-05: "Roll braucht man aber auch um die Antennenposition zu korrigieren"):

| # | where | formula | effect |
|---|---|---|---|
| 1 | `CGuidance.cs:98`, `CABLine.cs:290`, `CABCurve.cs:1004`, `CContour.cs:540` | `steerAngle += imuRoll * -sideHillCompFactor` | steering term |
| 2 | **`Position.designer.cs`** | `rollCorrectionDistance = Math.Tan(toRadians(imuRoll)) * -AntennaHeight`, added along the heading-perpendicular to **all three `stepFixPts`** | **POSITION offset** |
| 3 | `OpenGL`/`FormGPSData`/`CAHRS` | display; `rollZero` and `rollFilter` are user settings | display / smoothing |

Note it is `tan`, not `sin` (the comment in `HeadingBridge.cpp:1401` says sin - wrong), times
`-AntennaHeight` (VehicleSettings default 3 m). In AgIO there is only display/config
(`lblIMURoll`, the IMU dialog) - the correction itself is in the main app.

Measured position offset `tan(roll)*3 m` from the published roll:

| log | p50 | p90 | max | > 0.3 m | after /10: p50 / p90 |
|---|---|---|---|---|---|
| 17-09 F9P | 0.80 m | 2.17 m | 3.33 m | **73 %** | **0.08 / 0.22 m** |
| 17-18 F9P | 0.49 | 1.76 | 8.52 | 66 % | 0.05 / 0.18 |
| 17-28 UM982 | 0.15 | 0.32 | 9.02 | 10 % | 0.01 / 0.03 |
| 11-27 UM982 | 4.76 | 57 | -> inf at 90 deg | 68 % | 0.48 / 5.72 |
| 13-53 UM982 **without IMU** | **0.12** | **0.19** | 0.33 | **1 %** | 0.01 / 0.02 |

The healthy machine (no IMU, receiver roll) sits at 0.12/0.19 m. After the /10 the F9P lands at
0.08/0.22 m, i.e. in exactly that range - the strongest independent confirmation of the fix
available so far. Before it, AOG fabricated > 0.3 m of position offset in 73 % of the F9P
frames, and beyond the +-25 deg clamp the offset jumps between 0 and 1.4 m (tan(25)*3).

Why this did NOT become the diagonal: the offset is applied perpendicular to the heading, so a
mostly-constant roll error shifts the whole line parallel - the guidance still aligns the heading
with the line. The diagonal stays a HEADING issue (psi), which is why `fuse.ps1` remains the
open item.

Our own firmware does NOT do this correction (`NAVProcessor` only publishes the roll), so there
is no double correction; the pivot/antenna offset is a separate AOG feature (`AntennaOffset`).

* a small true roll -> **10x too much side-hill draft**;
* true roll > 2.5 deg -> the value exceeds +-25 and AOG **sets it to 0**: the side-hill draft
  switches OFF exactly on the slopes that need it (and back on below 2.5 deg);
* nobody sees an "absurd roll" in AOG because of that clamp - so "it arrives correctly" and
  "the value is 10x" can both be true.

In OUR firmware the roll also reaches the VWAS: `WheelAngleFusion.cpp:475`
(`rollDeg = headingBridge.getRollDeg()`, fallback `gpsData.dualRoll`, then `insRoll`) -> the VWAS
side-hill gain (boot log: 0.120 deg/deg) and its roll-binned zero learning (`bins=5` in the VWAS
zero line). On the F9P the IMU roll is the ONLY source (`roll_src=2` in 100 % of the frames), so
there the VWAS zero learning runs on a 10x roll.

|---|---|---|---|
| 20-03 | 67.5 / -147.1 | -147.7 | 6.8 / -14.7 |
| 20-11 | 73.7 / -161.6 | -163.7 | 7.4 / -16.2 |
| 11-27 | 109.3 / -125.9 | -92.7 | 10.9 / -12.6 |
| 17-09 | -4.5 / -67.4 | -3.9 | -0.5 / -6.7 |
| 17-18 | -1.2 / -42.1 | -9.5 | -0.1 / -4.2 |
| 17-28 | 30.3 / -159.5 | +31.4 | 3.0 / -16.0 |

Without the /10 these are physically impossible (a parked tractor pitched 67 ... 109 deg or rolled
126 ... 162 deg). With the /10 they are plausible park values. **The firmware carries 0.1 deg units
(the BNO085 RVC raw is 0.01 deg) while passing them on as degrees** - i.e. `rollX10`, exactly the
convention AOG's own PGN-211 path assumes. Same for pitch. Fix: the commented-out `* 0.1f`.

**The axis configuration changed between the drives:** on 10-01/10-02 `imu_roll` follows the boot
ROLL, on 10-04 it follows the boot PITCH -> the bridge read the BNO's roll on one day and its pitch
on the other (`isUseYAxis` swap). That is why a regression across drives found no consistent
relation at all: the same column held a different physical angle. **Log the axis config with every
log** and record it in the identification test.

1. The projection (Step A) + the ring look-back (Step C) is what the UM982 needs and the F9P

2. `qf`-based criteria are meaningless across machines: the F9P has `headingQuality = 0` in

4. `travel_wit` is invalid in ~100 % of the frames on both machines: the direction-of-travel
